## Context

yt-monitor skill 当前的工作流是线性自动化的：Claude 执行脚本 → 获取结果 → 直接处理。用户在关键决策点（添加哪个频道、检查哪些频道、总结哪些视频）没有参与机会。

现有脚本已经支持 `--json` 输出，数据结构完备，只需在 SKILL.md 的工作流层面引入 AskUserQuestion 交互节点即可，无需修改脚本代码。

## Goals / Non-Goals

**Goals:**

- 在频道添加、频道选择、视频选择三个关键决策点引入 AskUserQuestion 交互
- 利用现有脚本的 JSON 输出构建选择列表，零脚本改动
- 保持流程简洁，不强制交互——当上下文明确时（如用户指定了频道名）可跳过确认

**Non-Goals:**

- 不修改 Python 脚本代码
- 不引入新的脚本或工具
- 不改变现有的数据存储格式

## Decisions

### 决策 1：纯 SKILL.md 层面实现，不改脚本

**选择**：仅修改 SKILL.md 中的工作流描述，在关键步骤间插入 AskUserQuestion 节点。

**理由**：现有脚本的 `--json` 输出已包含所有需要展示给用户的信息（频道列表、视频列表），无需新增脚本功能。SKILL.md 本身就是 Claude 的行为指南，在这里定义交互逻辑最自然。

**替代方案**：在脚本中增加交互式模式 → 过度工程化，Claude Code 的 AskUserQuestion 工具已经提供了完善的交互能力。

### 决策 2：条件性交互，非强制

**选择**：根据上下文决定是否需要交互确认。

- 用户已明确指定频道名 → 跳过频道选择
- 只有 1 个新视频 → 跳过视频选择，直接处理
- 用户说「全部总结」→ 跳过视频选择

**理由**：避免不必要的交互打断流程，保持效率。

### 决策 3：AskUserQuestion 的选项格式

**选择**：使用编号列表展示选项，包含关键信息（频道名/视频标题+发布时间），支持多选。

**理由**：AskUserQuestion 支持预设选项，编号列表直观易选。视频选择场景需要多选能力（用户可能要总结其中几个）。

## Risks / Trade-offs

- **[交互步骤增多导致流程变慢]** → 通过条件性交互缓解：上下文明确时自动跳过
- **[用户不熟悉交互方式]** → AskUserQuestion 是 Claude Code 原生能力，用户已经习惯这种交互模式
- **[选项过多时列表过长]** → 视频列表默认只展示最近 7 天，数量可控；频道列表通常不超过 20 个
